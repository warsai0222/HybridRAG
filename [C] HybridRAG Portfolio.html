Query Embedding with BGE

The incoming claim is embedded using BAAI/bge-large-en-v1.5, an encoder-only transformer trained with contrastive learning. It maps semantically similar claims to nearby points in a 1024-dimensional vector space.


BGE uses an asymmetric strategy: documents are indexed as plain text, but queries are prefixed with "Represent this sentence for searching relevant passages:" - a signal to the model that we're searching, not indexing. Retrieval quality measurably drops without it.


Embeddings are L2-normalized so cosine similarity equals dot product - keeping all similarity scores consistent and comparable.

# Asymmetric embedding - core BGE insight

def embed_document(text):
# No prefix for indexing
return model.encode(text, normalize=True)

def embed_query(query):
prefix = "Represent this sentence "
"for searching relevant passages: "
return model.encode(
prefix + query,
normalize=True

Technical Stack

Every component, and why

Each technology was chosen for a specific reason. This isn't a framework - it's a deliberate design.

🔍
BGE-large-en-v1.5
Semantic retrieval backbone
Encoder-only transformer trained via contrastive learning. Leads MTEB English retrieval benchmarks. Understands paraphrases and conceptual similarity - critical for regulatory language where claim wording varies but meaning doesn't.
📊
BM25 (Okapi)
Keyword retrieval complement
Catches exact term matches dense embeddings miss: specific drug names, IND/NDA numbers, trial identifiers like MONALEESA-7, regulatory phrases like "adequate and well-controlled." Dense and sparse are architecturally complementary - neither alone is sufficient.
⚖️
Reciprocal Rank Fusion
Scale-invariant result fusion
Dense scores (cosine, 0–1) and sparse scores (BM25, unbounded) live on different scales - averaging them directly is mathematically meaningless. RRF uses only rank positions, making fusion robust regardless of score distribution. Cormack et al., 2009.
🐘
PostgreSQL + pgvector
Unified storage + vector search
One database handles structured document storage and approximate nearest-neighbor search via an HNSW index. No separate vector DB to maintain or sync - simpler operational footprint and one less failure point.
🤖
Llama 3.3 70B (Groq API)
Classification reasoning head
Receives the top-5 retrieved FDA enforcement examples as few-shot context and reasons about compliance under 21 CFR Part 202. Constrained to structured JSON output with label, confidence, and rationale fields.
⚡
FastAPI + Pydantic
Production-grade API layer
Type-safe request/response validation, auto-generated OpenAPI docs, async-ready request handling. Pydantic-settings manages config - secrets stay in .env, never in source. CORS-enabled so the portfolio demo works as a local file.
Why MLR review needs this
Every promotional claim must pass Medical-Legal-Regulatory review before reaching physicians or patients. A single non-compliant claim can trigger an FDA enforcement action - as seen in the 70+ OPDP untitled letters issued to Pfizer, Novartis, AbbVie, AstraZeneca, and Novo Nordisk. HybridRAG gives MLR reviewers an AI-powered first pass that cites real regulatory precedent, not synthetic examples.
Why hybrid beats either alone
Dense retrieval understands semantic similarity - "reduces cardiac events" and "lowers heart attack risk" are the same idea. Sparse BM25 catches exact terms - a trial name like MONALEESA-7, a regulatory phrase like "adequate and well-controlled studies". RRF fuses both rankings into a single list that consistently outperforms either retriever alone on domain-specific text.
📋
Data Source - FDA OPDP Enforcement Letters
The retrieval index is built from real FDA Office of Prescription Drug Promotion (OPDP) untitled letters scraped from fda.gov and parsed with pdfplumber. Each claim is labeled by violation type - false balance, unsubstantiated, off-label, comparative - directly from the FDA's own findings. No synthetic data. Source: fda.gov/opdp

AI-Assisted Classification - Research Prototype

HybridRAG uses an LLM with hybrid retrieval to classify pharma promotional claims for MLR compliance. This is a research prototype and is not a substitute for qualified Medical-Legal-Regulatory review.

  • AI verdicts may be incorrect, incomplete, or contextually inappropriate.
  • All outputs should be reviewed by a qualified MLR professional before action.
  • Knowledge base is limited to ingested FDA OPDP data; may not reflect current guidance.
  • Confidence scores are model estimates, not guarantees of accuracy.
AI DISCLAIMER Research prototype - not for regulatory use. All verdicts require human MLR review. Low-confidence outputs are automatically flagged for expert review.
