HybridRAG — Build Lifecycle & File Reference

Every file in the project, what it does, and why it comes at that point in the build order.

Step 1 Project Scaffold

Before writing a single line of application code, you set up the skeleton — everything that makes the project reproducible, safe, and runnable by anyone on any machine. These files have no logic in them; they're configuration and infrastructure declarations.

.gitignore Tells git which files to never commit. Critical entries: .env (secrets), .venv/ (local packages), __pycache__/ (compiled bytecode). Without this, your API keys go public the moment you push.
requirements.txt The full list of Python packages the app depends on — fastapi, sqlalchemy, sentence-transformers, rank-bm25, openai, pydantic-settings, etc. Anyone cloning the repo runs pip install -r requirements.txt and gets an identical environment.
.env Stores real secrets: API keys, DB credentials. Never committed. Loaded at runtime by pydantic-settings. This is the only place secrets should ever appear.
.env.example A committed template showing what keys are needed, but with empty values. Teammates copy this to .env and fill in their own credentials.
docker-compose.yml Defines and starts your infrastructure with one command (docker compose up). For HybridRAG this spins up Postgres with the pgvector extension pre-installed. Without this you'd need Postgres installed locally and configured by hand — fragile and non-reproducible.
Makefile Shortcut commands so you don't memorize flags. make api starts the FastAPI server. make db starts Postgres. make ingest seeds the database. Makes the project easier to run and demo.
↓
Step 2 Configuration

Every file in the project needs shared values — the DB URL, model names, retrieval depths. Config is the single source of truth for all of them. It gets built before anything else because every subsequent file imports from it.

src/config.py Defines a Settings class using pydantic-settings. Reads values from .env at startup, validates their types, and exposes them as typed attributes. An @lru_cache wrapper ensures .env is parsed exactly once — every module that calls get_settings() gets the same cached object.
↓
Step 3 Database Layer

The database is the foundation everything else reads from and writes to. The schema defines the structure; the database module defines every query. All other files call into this module — nothing else talks to Postgres directly. This boundary means if you ever change your DB, you only change one file.

scripts/init.sql Creates the three tables (documents, embeddings, classification_log) and their indexes. Runs once when Postgres starts via docker-compose. Defines the HNSW index on embeddings for fast approximate nearest-neighbor search, and the partial index on classification_log for the review queue.
src/database.py Owns the SQLAlchemy engine (connection pool), the session context manager, and every SQL query function: insert_document, insert_embedding, search_dense (pgvector cosine search), get_all_documents (for BM25), and log_classification. Acts as a data access layer — no business logic, just queries.
↓
Step 4 Ingestion

Before retrieval can work, the database needs to be populated with labeled examples. Ingestion is the pipeline that takes raw text, converts it to a dense vector using the BGE embedding model, and stores both the text and the vector in Postgres. The retrieval layer depends entirely on data being here first.

src/ingestion/ingest.py Loads the BGE model (once, as a singleton). Exposes two embedding functions: embed() for documents (no prefix) and embed_query() for queries (with the BGE retrieval prefix). Calls insert_document and insert_embedding from database.py for each document ingested.
scripts/ingest_samples.py A one-time script that reads your 50 labeled pharma claims and calls ingest_documents() to seed the database. Run this once after the DB is up and before starting the API. This is your knowledge base — the ground truth the classifier learns from at inference time.
↓
Step 5 Retrieval

Given a new claim, the system needs to find the most similar labeled examples to use as few-shot context for the LLM. Two retrieval methods run in parallel — one semantic (dense), one keyword-based (sparse) — then get fused into a single ranking. Using both catches what either alone would miss.

src/retrieval/dense.py Embeds the incoming query with embed_query(), then calls search_dense() from database.py to find the closest vectors by cosine similarity using pgvector. Returns the top-K most semantically similar documents. Good at understanding meaning even when words differ.
src/retrieval/sparse.py At startup, loads all documents from the DB and builds an in-memory BM25 index. At query time, tokenizes the query and scores every document by term frequency and inverse document frequency. Good at exact keyword matches that dense embeddings can miss (e.g., drug names, regulatory codes).
src/retrieval/fusion.py Takes the ranked lists from dense and sparse retrieval. Applies Reciprocal Rank Fusion: for each document, sum 1/(k + rank) across both lists where k=60 is a smoothing constant. Higher score = appeared near the top of both lists. Returns the top-K fused results. RRF uses rank positions only — not raw scores — making it robust to scale differences between methods.
↓
Step 6 Classifier

The retrieved examples become few-shot context for an LLM. The LLM reads the labeled examples alongside the new claim and reasons about which compliance category it belongs to. This is the intelligence layer — everything before it was about finding the right context to put in front of the model.

src/classifier/classify.py Calls retrieve_hybrid() to get the top fused examples. Formats them as a few-shot prompt with MLR regulatory context and verdict definitions. Calls the Groq API (Llama 3.3 70B) with response_format=json_object to get a structured response. Parses the label, confidence, and rationale. Flags predictions below 0.7 confidence for human review. Logs every result — including failures — to classification_log.
↓
Step 7 API Layer

The classifier is a Python function — the API turns it into an HTTP service that anything can call: a UI, a mobile app, another service, or a curl command. FastAPI handles request validation, response serialization, and auto-generates OpenAPI docs at /docs.

src/api/main.py Defines the FastAPI app with four endpoints: POST /classify (classify a claim), POST /ingest (add documents), GET /health (DB + model status), GET /review-queue (low-confidence predictions needing human review). Uses Pydantic models for request/response validation. On startup, builds the BM25 index from existing documents.
↓
Step 8 UI + Eval

The UI is how you demo the project to anyone non-technical. The eval script is how you prove it works — accuracy, precision, and recall over a labeled test set. Both are built last because they depend on everything else being complete and working.

ui/app.py Streamlit app. Text input box for a pharma claim → calls POST /classify → displays the verdict badge, confidence score, rationale, and the retrieved reference examples. This is what a recruiter or MLR reviewer sees. Requires only the API to be running.
src/eval/evaluate.py Loads a held-out labeled test set. Runs each claim through classify(). Computes accuracy, per-label precision, recall, and F1. Reports average latency and the distribution of confidence scores. This is what goes in the README and portfolio write-up as proof of performance.

End-to-End Data Flow at Inference Time

Claim text in → BGE embeds query → Dense + Sparse retrieval → RRF fusion → LLM few-shot prompt → Verdict + rationale out
