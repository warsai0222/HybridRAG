Interview Q&A - HybridRAG

Q: Walk me through the project at a high level.
HybridRAG is a pharma MLR compliance classifier that takes a pharmaceutical promotional claim and classifies it into one of 6 categories - supported, unsupported, partially supported, false balance, needs legal review, or insufficient data. It works by retrieving the most relevant real FDA enforcement actions (OPDP untitled letters) using a hybrid of dense semantic search and sparse BM25 keyword search, fuses the results with Reciprocal Rank Fusion, then feeds the top-5 as few-shot examples to Llama 3.3 70B to reason about compliance. The key insight is that the LLM doesn't need to memorize FDA regulations - it reasons over retrieved evidence at inference time.
Q: Why hybrid retrieval? Why not just use dense embeddings?
Dense retrieval (BGE + pgvector) catches semantic similarity - "reduces cardiac events" and "lowers heart attack risk" map to nearby points in vector space even though they share zero words. But it misses exact term matches. BM25 catches what dense misses: a specific drug name like KISQALI, a trial identifier like MONALEESA-7, or regulatory language like "adequate and well-controlled studies." These are critical in pharma where exact terminology matters for legal precedent. The two retrievers are architecturally complementary - neither alone is sufficient.
Q: What is RRF and why use it instead of score averaging?
RRF stands for Reciprocal Rank Fusion (Cormack et al., 2009). The formula is: RRF(d) = sum of 1/(k + rank(d)) across all retrieval lists, where k=60. The critical insight is that dense scores (cosine similarity, range 0-1) and sparse scores (BM25, unbounded) live on completely different scales - averaging them directly is mathematically meaningless. RRF uses only rank positions, making it scale-invariant. A document ranked #1 by both retrievers gets the highest score regardless of what the raw scores were. This consistently outperforms score-based fusion on BEIR benchmarks.
Q: Why BGE specifically? Why not OpenAI embeddings?
BGE-large-en-v1.5 by BAAI leads the MTEB English retrieval benchmarks. It uses an asymmetric strategy: documents are indexed as plain text, but queries get a prefix - "Represent this sentence for searching relevant passages:" - which signals the model it's doing search, not indexing. Retrieval quality measurably drops without this prefix. Embeddings are L2-normalized so cosine similarity equals dot product. Compared to OpenAI embeddings: lower latency (runs locally), no per-call cost at scale, and no data leaving the system - important for pharma regulatory data.
Q: Where does the training data come from?
Real FDA OPDP untitled letters scraped from fda.gov. These are enforcement actions where the FDA cited specific promotional claims as violating 21 CFR Part 202. The labels aren't synthetic - they come from the FDA's own categorization of violations: false or misleading efficacy claims, omission of risk information, off-label promotion, unsubstantiated comparative claims, etc. The scraper downloads each PDF, extracts text with pdfplumber, splits into violation sections by regex, extracts the specific cited claims using 5 strategies (bullets, numbered lists, inline quotes, "statement: X" patterns, prose fallback), and assigns one of 5 compliance labels via keyword-priority rules.
Q: How does the confidence threshold work?
The LLM returns a confidence score (0.0 to 1.0) alongside the label and rationale. If confidence is below 0.70, the result sets needs_human_review: true - signaling that a qualified MLR professional should review rather than acting on the AI verdict directly. There's also a separate check: if the maximum RRF score across all retrieved documents is below 0.015, it means no relevant precedent exists in the knowledge base, and the label becomes insufficient_data rather than guessing.
Q: Why Groq / Llama instead of OpenAI?
Groq's LPU inference engine delivers 400+ tokens/second on Llama 3.3 70B - roughly 10-20x faster than OpenAI API for the same capability tier. The Groq API is OpenAI-compatible (same client library, just swap base URL and model name), so there's zero migration cost. For a RAG system where the LLM is the last step in a pipeline, inference latency matters - faster LLM means faster end-to-end classification. Llama 3.3 70B is competitive with GPT-4o on reasoning tasks while being free at the inference layer via Groq's free tier.
Q: What is RAGAS and how did you use it here?
RAGAS is an LLM-as-judge evaluation framework originally designed for QA systems. I adapted it to a classifier by framing each test case as: question = "Classify this pharma claim for MLR compliance: {claim}", answer = "{label}: {rationale}", contexts = retrieved FDA precedents, ground_truth = expert-written verdict. RAGAS measures Faithfulness (is the answer supported by the contexts?), Answer Relevance (does the answer address the question?), Context Precision (are the top-ranked contexts relevant?), Context Recall (are all needed contexts retrieved?), and Answer Similarity (how close is the predicted label to the ground truth?). The eval harness in src/eval/eval_ragas.py also runs standard accuracy, F1, calibration, and latency metrics.

System Specs - Quick Reference

Retrieval
BGE-large-en-v1.5 (1024-dim) · pgvector HNSW · BM25 Okapi · top-10 each · RRF k=60 · top-5 final
LLM
Llama 3.3 70B via Groq API · OpenAI-compatible client · JSON mode output · ~1.2s latency
Storage
PostgreSQL + pgvector (single DB for structured + vector) · BM25 in-memory (RAM) · PDF cache on disk
Labels (6)
supported · unsupported · partially_supported · false_balance · needs_legal_review · insufficient_data
API
FastAPI · Pydantic · POST /classify · GET /health · auto OpenAPI docs at /docs · CORS-enabled
