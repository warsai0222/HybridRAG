# HybridRAG — Pharma MLR Claim Classifier

A production-grade compliance classification system that uses Retrieval-Augmented Generation to classify pharmaceutical marketing claims against FDA OPDP enforcement letter precedents. Instead of training a model on labeled data, it retrieves real enforcement examples and uses them as evidence for LLM reasoning.

**Domain:** Pharma MLR (Medical, Legal, Regulatory) compliance  
**Data source:** Real FDA OPDP Untitled Letters (scraped, parsed, labeled)  
**Stack:** Python · PostgreSQL + pgvector · BGE embeddings · BM25 · GPT-4o · FastAPI

---

## How It Works — 4 Stages

The system is built in four distinct layers. Each one has a clear job, and they only hand off to the next once their job is done.

---

## Stage 1 — Data Foundation

**The job:** Turn raw FDA enforcement letters into clean, labeled examples the system can learn from.

### The Problem It Solves

The system needs to know what a violation looks like before it can classify anything. That knowledge doesn't come from training — it comes from real FDA enforcement history. Stage 1 is entirely about acquiring that knowledge and storing it in a way the retrieval layer can query efficiently.

### What Happens

**1. Scraping** (`scripts/scrape_fda_opdp.py`)

The FDA publishes a public table of Untitled Letters at [fda.gov/drugs/warning-letters-and-notice-violation-letters](https://www.fda.gov/drugs/warning-letters-and-notice-violation-letters-pharmaceutical-companies/untitled-letters). Every row is a real enforcement action — company name, drug name, date, and a link to the PDF.

The scraper:
- Fetches the HTML table and extracts each row
- Downloads each PDF (caching to `data/pdf_cache/` so re-runs skip downloads)
- Parses the PDF text using `pdfplumber`
- Splits the letter into named sections (Background, Issue 1, Issue 2, etc.)
- Extracts the actual violating claims from each section
- Assigns a compliance label based on which type of violation section it came from

**2. Label Assignment**

The FDA letter structure makes labeling systematic. Section headers map directly to violation types:

| Section keyword | Label assigned |
|---|---|
| omission / risk information | `false_balance` |
| off-label / superiority | `needs_legal_review` |
| unsubstantiated | `unsupported` |
| overstatement / misleading | `partially_supported` |

**3. Storage** (`src/ingestion/ingest.py`)

Each extracted claim is stored as a row in PostgreSQL with:
- `text` — the raw claim string
- `label` — compliance verdict
- `embedding` — a 1024-dimensional dense vector (generated by BGE)
- `metadata` — drug name, company, letter date, FDA URL

The `pgvector` extension on PostgreSQL lets the database store and query those embedding vectors directly, without a separate vector database service.

**Output:** `data/fda_opdp_raw.jsonl` — one claim per line, ready to ingest

**4. PI Documents** (`scripts/ingest_pi_documents.py`)

To balance the knowledge base — FDA enforcement letters are naturally skewed toward violation labels — the system also ingests claims from FDA-approved prescribing information (PI) documents via the FDA Label API (`api.fda.gov/drug/label.json`).

- `clinical_studies` sections → labeled `supported` (full trial evidence with statistics)
- `indications_and_usage` sections → labeled `partially_supported` (approved language, no outcome statistics)

These are ingested through the same validation pipeline as enforcement letters, with a per-label cap to prevent any single source from dominating the knowledge base.

**5. Validation + Ingestion Pipeline** (`scripts/run_ingestion_pipeline.py`, `src/ingestion/validate.py`)

Every document passes through a two-stage validation gate before reaching the knowledge base:

- **Rule-based validation (free):** Label allowlist, text length bounds, source domain allowlist, boilerplate detection, claim structure check. Most documents are cleared or rejected here at zero API cost.
- **LLM validation (batched):** Borderline documents are batched into groups of 10 and sent to a single LLM call. This is the agent harness pattern — LLM is only called when rules are insufficient, and always in batches to minimize cost.
- **SHA-256 deduplication:** Documents are fingerprinted before embedding. Re-ingesting the same source produces no duplicate rows — the pipeline is idempotent.
- **Review queue:** `supported` claims and anything the rule check can't confidently clear go to a review queue for human approval before entering the live knowledge base.

### Key Design Decisions

**Why not train a classifier?** Training requires thousands of labeled examples. FDA enforcement letters give you ~hundreds at most. RAG lets you use small datasets effectively by keeping the examples as retrieval targets rather than training signal.

**Why PDF parsing instead of HTML?** Every FDA OPDP letter is published as a PDF — the HTML page is just a listing with links. There is no HTML version of the letter content. `pdfplumber` extracts cleaner text than PyPDF2 for government document layouts.

**Why cache PDFs?** The FDA server is slow and the scraper is re-run frequently during development. MD5-hashed filenames mean a 200-letter corpus downloads once and never again.

**Why the agent harness pattern?** Calling an LLM on every document during ingestion would cost ~$0.01 per document — for 800 scraped claims that's $8 per ingestion run. Rule-based pre-filtering clears ~80% of documents for free; the LLM only handles the ambiguous 20%, and in batches of 10. Typical cost: under $0.10 per full refresh.

### Interview Talking Points

- "We built a data pipeline that turns unstructured government PDFs into structured training examples without any manual labeling."
- "Label assignment uses the FDA's own section structure — the letter literally tells you what type of violation it is."
- "We cache downloads by content hash, so iterating on the extraction logic doesn't re-hit the FDA server on every run."
- "The ingestion pipeline uses an agent harness pattern — rules first, LLM only for borderline cases in batches. It cuts validation API cost by ~80%."
- "SHA-256 deduplication makes the pipeline idempotent — re-running the scraper never produces duplicate KB entries."

## Stage 2 — Retrieval

**The job:** Given a new claim to classify, find the most relevant labeled examples from the database — fast and accurately.

### The Problem It Solves

When you submit "Ozempic reduces cardiovascular risk in all patients," the system needs to find stored FDA examples that are most similar to that claim — so it can reason by analogy. The question is: what does "similar" mean?

Stage 2 runs two different similarity searches in parallel and combines their results.

### Two Retrievers, One Answer

**Dense Retrieval (BGE embeddings)**

The claim is converted into a 1024-dimensional vector using `BAAI/bge-large-en-v1.5`. This vector encodes semantic meaning — claims about omitting risk information will cluster near each other in vector space, even if they use completely different words.

- Fast: one vector comparison against all stored embeddings using pgvector's HNSW index
- Good at: finding semantically similar claims, handling paraphrases
- Bad at: exact keyword matching, rare drug names, regulatory jargon

**Sparse Retrieval (BM25)**

BM25 is a keyword scoring algorithm (the same one that powers Elasticsearch). It ranks stored examples by how many important words they share with the query — weighted by how rare those words are across the corpus.

- Fast: pure math, no neural network
- Good at: exact terminology like "KISQALI", "MONALEESA-7", "cardiovascular outcomes trial"
- Bad at: paraphrases or claims that use different words for the same concept

**Why Both?**

Dense retrieval catches meaning. Sparse retrieval catches terminology. Neither alone is reliable for regulatory text, which mixes clinical jargon (specific drug names, trial names) with natural language reasoning (implied claims, omissions).

Running both and combining their results covers the failure modes of each.

### Score Fusion (RRF)

The two retrievers return ranked lists. To merge them, Reciprocal Rank Fusion (RRF) is used:

```
score = 1 / (k + rank_dense) + 1 / (k + rank_sparse)
```

Where `k = 60` is a dampening constant. The key insight: a result that ranks 3rd in both lists beats a result that ranks 1st in one and 200th in the other. Consistency across retrievers is a strong signal of relevance.

The top-5 results after fusion become the evidence set for Stage 3.

### Key Design Decisions

**Why BGE instead of OpenAI embeddings?** BGE-large runs locally, costs nothing per query, and benchmarks competitively with text-embedding-3-large on retrieval tasks. At scale, embedding API costs add up fast.

**Why BM25 instead of a second vector model?** BM25 is complementary by design — it operates on completely different signals (term frequency) than dense vectors (semantic geometry). Adding a second neural encoder would be redundant.

**Why k=60 in RRF?** Lower k values over-reward rank #1. k=60 ensures that consistently mid-ranked results (good in both retrievers) beat a single top hit (great in one, absent in the other). This produces more stable results across diverse query types.

**What about chunking?** Chunking is only needed when source documents are long and you need to retrieve specific passages from within them. Here, each stored example is already atomic — a single claim extracted from a specific paragraph of an enforcement letter. No chunking needed.

### Interview Talking Points

- "We run two retrievers in parallel — dense for semantics, sparse for terminology — and fuse their rankings with RRF."
- "BM25 catches drug names and trial names that embeddings sometimes miss because they're rare in training data."
- "RRF with k=60 rewards consistency over lucky rank-1 hits. It's more robust across query types."
- "BGE embeddings run locally — no API cost, no latency added by a remote call, no third-party dependency in the hot path."

## Stage 3 — Classification

**The job:** Use the retrieved examples as evidence to classify the new claim, assign a confidence score, and write a rationale that cites those examples.

### The Problem It Solves

You now have a claim and 5 similar enforcement precedents. Stage 3 is where the actual decision happens. The LLM doesn't classify from general knowledge — it classifies by reasoning about the retrieved evidence. This is the key distinction from just asking ChatGPT.

### How Classification Works

**The Prompt**

The 5 retrieved examples are injected into the prompt as numbered evidence items:

```
You are an FDA MLR compliance reviewer.

Classify the following claim based on the enforcement precedents below.

Evidence:
[1] "Ozempic significantly reduces cardiovascular events in patients with type 2 diabetes"
    → Label: false_balance
    → Source: Novo Nordisk Untitled Letter, March 2023

[2] "Treatment with semaglutide leads to superior cardiovascular outcomes"
    → Label: needs_legal_review
    → Source: Novo Nordisk Untitled Letter, June 2022

... (5 examples total)

Claim to classify: "Ozempic reduces cardiovascular risk in all patients"

Return: label, confidence (0.0–1.0), rationale (cite examples by number)
```

**Few-Shot Reasoning**

The retrieved examples function as few-shot examples — they show the LLM what a violation in this specific domain looks like, grounded in real FDA decisions. The LLM isn't guessing from training data; it's reasoning from precedent.

**Confidence Scoring**

The LLM returns a confidence value between 0 and 1. This isn't raw model probability — it's the LLM's own assessment of how strongly the evidence supports its verdict. A score below 0.70 flags the prediction as `needs_human_review: true`, which queues it for manual review via the `/review-queue` endpoint.

### Hallucination Mitigation

The most common interview question: *"How do you know the LLM isn't making up the rationale?"*

Three layers of protection:

**1. Citation anchoring.** The prompt instructs the LLM to cite examples by their number ("[1]", "[2]", etc.). The rationale must be traceable back to specific retrieved documents. If it cites example [3], you can pull example [3] from the database and verify it actually says what the rationale claims.

**2. Label accuracy eval.** The eval harness (`src/eval/`) runs the classifier over a held-out test set with known labels and measures F1 and accuracy. If the LLM is routinely confusing `false_balance` with `unsupported`, it shows up in precision/recall per label — and you can trace it to specific misclassified examples to understand why.

**3. Confidence thresholding.** A confident but wrong answer is more dangerous than an uncertain one. Setting `needs_human_review: true` at confidence < 0.70 ensures that low-confidence predictions get human eyes before any action is taken.

**Example of a caught hallucination:**

Claim: *"KISQALI combined with letrozole shows superior efficacy versus all other CDK4/6 inhibitors"*

LLM output:
- Label: `needs_legal_review` ✓ (correct)
- Rationale: *"Similar to examples [2] and [4] which involved unsubstantiated superiority claims about KISQALI in the MONALEESA-3 trial"* ✗

But examples [2] and [4] were about a different drug (Ibrance). The LLM fabricated the citation mapping. The eval harness flags this because the label was correct but the reasoning was detached from actual evidence — caught during a manual review of low-confidence predictions.

### Key Design Decisions

**Why GPT-4o instead of a local model?** The classification prompt requires structured JSON output, chain-of-thought reasoning over 5 examples, and reliable instruction-following. GPT-4o is the most consistent at this. Local models like Llama 3 struggle with precise JSON formatting under complex prompts.

**Why not just ask ChatGPT directly?** ChatGPT's knowledge of any specific enforcement letter is uncertain and unverifiable. By injecting real FDA letter excerpts into the prompt, you know exactly what evidence the LLM is reasoning from. You can audit the decision, version the evidence, and trace any output back to a specific source document.

**Why 0.70 as the confidence threshold?** It's calibrated to the distribution of the current knowledge base. If the KB has 150 examples and the top retrieved result has a BM25 score below a certain threshold, the LLM tends to hedge — and those predictions tend to be wrong. 0.70 was chosen by running the eval harness and finding where precision drops sharply.

### Interview Talking Points

- "The LLM reasons from retrieved enforcement precedents, not from its training data. Every output is traceable to a source document."
- "We require citations by example number — if the rationale cites [3], you can pull example [3] and verify it says what the rationale claims."
- "Confidence thresholding at 0.70 routes uncertain predictions to a human review queue — so low-confidence outputs never trigger automated actions."
- "We run an F1 eval on a held-out test set after every knowledge base update. If a change tanks precision on a label, we catch it before it ships."

## Stage 4 — Application Layer

**The job:** Expose the full system as a usable product — a REST API, a demo UI, a data pipeline, and an eval harness — so the work done in Stages 1–3 is actually accessible and verifiable.

### Components

**REST API** (`src/api/main.py` · FastAPI)

Five endpoints that make the full pipeline accessible:

| Endpoint | Method | What it does |
|---|---|---|
| `/classify` | POST | Classify a single claim — runs full retrieval + LLM pipeline |
| `/ingest` | POST | Add new documents to the knowledge base |
| `/health` | GET | Database connectivity + label list check |
| `/labels` | GET | List all valid compliance verdict labels |
| `/review-queue` | GET | Return recent predictions with confidence < 0.70 |

The API is stateless — it reads from PostgreSQL on every request. No in-memory model state means it can be horizontally scaled and restarted without loss.

**Security Layer** (`src/api/security.py`)

Because this API passes user input directly into an LLM prompt, the application layer is a natural target for prompt injection attacks. The security module guards against this at the API boundary — before any input reaches the prompt builder:

- **Prompt injection detection:** 14 regex patterns covering instruction overrides ("ignore previous instructions"), role-switching ("act as a different AI"), jailbreak tokens (DAN, DevMode), system delimiter injection (`[INST]`, `<|system|>`), and data exfiltration probes ("repeat your system prompt").
- **Control character stripping:** Null bytes and non-printable C0/C1 characters are removed before pattern matching, preventing encoding tricks like `ign\x00ore` slipping through.
- **Input length bounds:** Hard cap at 2,000 characters. A real pharmaceutical claim is never this long — anything longer is almost certainly token stuffing.
- **Rate limiting (SlowAPI):** 30 requests/minute on `/classify`, 10/minute on `/ingest`, keyed by IP address.
- **CORS locked down:** In development, allows `localhost` ports and `file://` origins. In production, reads from the `ALLOWED_ORIGINS` environment variable — no wildcard origins in prod.
- **Security response headers:** Every response carries `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy`, HSTS, and `Referrer-Policy: no-referrer`.

**Demo UI** (`[C] HybridRAG Portfolio.html`)

A single-file HTML/JS portfolio page with two tabs:

- **Classify tab:** Text input → calls `/classify` → renders label, confidence bar, rationale, and the retrieved supporting examples
- **Review queue tab:** Calls `/review-queue` → table of predictions needing human review

The demo is intentionally self-contained (no build step, no npm) so it can be opened in any browser and demoed instantly in an interview.

**FDA Data Pipeline** (`scripts/scrape_fda_opdp.py` + Makefile)

The full data workflow is runnable via `make`:

```bash
make scrape-fda          # Scrape all FDA OPDP untitled letters
make scrape-fda-quick    # Scrape most recent 20 (dev/testing)
make ingest-fda          # Load scraped JSONL into PostgreSQL
make eval                # Run F1 + accuracy eval on held-out set
```

This makes the data pipeline reproducible — anyone can clone the repo and rebuild the knowledge base from scratch.

**Eval Harness** (`src/eval/`)

Runs after every knowledge base change:
- **F1 per label:** Catches label-specific degradation (e.g., `false_balance` precision drops after new data is ingested)
- **Accuracy overall:** Single headline metric
- **Latency:** End-to-end time from `/classify` call to response (target: <2s)
- **Confidence calibration:** Are 80%-confidence predictions right ~80% of the time?

### Key Design Decisions

**Why FastAPI?** It generates OpenAPI docs automatically (visible at `/docs`), handles async I/O cleanly, and is the de facto standard for Python ML APIs. Any AI engineering JD that mentions REST APIs expects FastAPI familiarity.

**Why a single-file HTML demo?** Zero dependency demos are reliable for interviews. No "let me install node_modules" moments. Open the file, point at a running API, it works.

**Why Makefile?** Makefiles are the standard for scripting multi-step dev workflows in Python ML projects. They're readable, they document the workflow, and they make the project easy for a hiring manager to run themselves.

**Why block at the API layer rather than relying on LLM resistance?** LLM resistance to prompt injection is inconsistent and model-dependent. A pattern-matched block at the API boundary is deterministic — it either matches or it doesn't. Belt + suspenders: block what you can identify structurally, then let the LLM handle the rest.

### Interview Talking Points

- "The API is stateless — all state lives in PostgreSQL. That means it can be scaled horizontally and restarted cleanly."
- "The review queue endpoint surfaces low-confidence predictions for human review — it's an active learning loop in embryo."
- "The eval harness runs F1 per label, not just overall accuracy. Overall accuracy hides label imbalance; per-label F1 doesn't."
- "The demo is a single HTML file — no build step, opens in any browser. I can demo the live API in an interview in under 30 seconds."
- "The API has a dedicated security layer — 14 regex patterns block prompt injection before the input ever reaches the prompt builder. We don't rely solely on LLM resistance because that's inconsistent."

## Running the Project

```bash
# 1. Start PostgreSQL (with pgvector)
docker-compose up -d

# 2. Install dependencies
pip install -r requirements.txt

# 3. Set environment variables
cp .env.example .env
# → Add GROQ_API_KEY and DATABASE_URL

# 4. Scrape + ingest FDA enforcement letters
make scrape-fda-quick    # ~20 letters for a fast start
make ingest-fda

# 5. Ingest PI documents (adds supported / partially_supported examples)
python scripts/ingest_pi_documents.py --limit 50
python scripts/run_ingestion_pipeline.py --input data/pi_claims_raw.jsonl --skip-llm --max-per-label 30
python scripts/run_ingestion_pipeline.py --input data/pi_claims_review.jsonl --skip-llm
python scripts/run_ingestion_pipeline.py --approve-all-pending

# 6. Check label balance
python scripts/diagnose_label_skew.py

# 7. Start the API
uvicorn src.api.main:app --reload

# 8. Open the demo
open "[C] HybridRAG Portfolio.html"

# 9. Run eval
python scripts/build_eval_set.py
python -m src.eval.evaluate --data data/eval/eval_large.jsonl
```
